# Monads: Making Structured Computations Compose

Suppose a function that looks up a person's supervisor may return a name or may fail because the information is missing. Another function looks up the supervisor of that supervisor and may also fail. How do we combine these operations without writing a new missing-data check at every step? We want a general rule: apply the first lookup; if it fails, stop with failure; if it succeeds, pass the name to the second lookup.

This is an example of structured computation. An ordinary function from A to B produces exactly one output in B. A lookup that may fail is more accurately modeled as a function from A to a type of optional B values. That type has a normal B-value case and a missing-value case. When we compose two lookups, we need a rule for handling the optional structure that appears in the intermediate result.

Category theory packages such rules into a structure called a monad. The word has acquired a reputation for mystery, especially in programming discussions. We will derive the definition from two familiar data types: optional values and lists. In both cases, the central operation is flattening a nested structure, or equivalently chaining computations that return structured results.

The mathematical definition of a monad is a functor equipped with two natural transformations satisfying three equations. Those equations express that inserting a plain value and then flattening does nothing, and that flattening a three-level nested structure does not depend on how we group the flattening steps. These are variations on identity and associativity, the same elementary laws with which category theory began.

## Optional values: success or missing

For each set A, define Maybe of A to be the set consisting of all values of A, tagged as present, together with one additional missing value. The tag prevents ambiguity: if A itself happens to contain a symbol called missing, that symbol as a present value remains distinct from the special missing case.

A function f from A to B can be lifted to a function from Maybe of A to Maybe of B. Apply f to a present value and keep the result present. Send missing to missing. This assignment preserves identity and composition, so Maybe is a functor on Set.

Now consider a value of Maybe of Maybe of A. There are three distinct logical possibilities: outer missing; outer present containing inner missing; or outer present containing inner present a. We can flatten this into Maybe of A by sending the first two cases to missing and the third case to present a.

For instance, a request to obtain a supervisor might itself be missing, or it might succeed but report that no supervisor exists, depending on how a system models the result. Flattening collapses two layers of optionality. In a real application one may want to preserve the distinction between different failure causes, but the simple Maybe monad intentionally does not keep both layers. The mathematical definition describes exactly this behavior.

There is also a way to insert an ordinary A-value into Maybe of A: tag it as present. Call this insertion the unit. We now have a functor, an insertion operation, and a flattening operation. That is the data of a monad, provided the three laws hold.

## Check the laws by cases

The first unit law says that if we take a Maybe value, insert it into an extra outer Maybe layer, and then flatten, we get the original Maybe value. If the original was missing, we inserted it as a present inner missing and then flattened to missing. If the original was present a, we inserted it as a present inner present a and flattened to present a. Both cases return the original.

The second unit law says that if we start with a Maybe value and apply the insertion operation to its inside value where present, then flatten, we again get the original. Missing remains missing, and present a becomes present present a, then flattening removes one layer. The two unit laws concern different ways to add an extra layer before flattening.

The associativity law concerns three layers of optionality. We can flatten the inner two layers first and then the result, or flatten the outer two first and then the result. Any nested value is either missing at some layer or eventually contains an actual a. Both routes return missing if any required layer is missing, and present a if all layers contain present tags. The two compositions agree.

This case analysis is a complete proof of the monad laws for Maybe. Nothing in it requires a story about programs. A monad is a precise algebraic structure on an endofunctor; an endofunctor is simply a functor from a category back to itself.

In a programming language, the same laws guide a convenient way to compose computations with optional outputs. We must still respect evaluation details and the model of the programming language. In particular, language-level exceptions, mutable state, or divergence may introduce behavior beyond the pure set-theoretic Maybe model.

## Lists: the same laws, a different meaning

Take the list functor L. It sends a set A to all finite lists of A-values, and a function f to the operation of applying f entrywise. There is an insertion map that sends an element a to the one-element list containing a. There is a flattening map that concatenates a list of lists into a single list.

For example, the nested list containing the list a,b and then the list c becomes the flat list a,b,c. If the nested list contains an empty list between those two entries, the empty contribution disappears under concatenation. If the outer list is empty, flattening returns the empty list.

The left unit law says that wrapping a list as a singleton outer list and then concatenating returns the original list. The right unit law says that turning each element of a list into its own singleton list and concatenating those singleton lists returns the original list. Both statements are familiar properties of concatenation.

The associativity law concerns a list of lists of lists. We can concatenate each inner group first, then concatenate the resulting lists, or concatenate the outer groups first and flatten the resulting list of lists. The final sequence of entries is identical and in the same order. This is associativity of concatenation expressed at the level of the list functor.

The list monad and the Maybe monad have the same formal shape, but their interpretations differ. Maybe models a computation with at most one successful result. Lists model a computation that returns any finite number of results, with order and multiplicity retained. One missing supervisor becomes a failure; a list of possible supervisors represents a branching calculation.

It is the structure and the laws, rather than the application story, that make both instances of the same definition.

## Chaining structured results

Suppose f takes an element of A and returns a list of B-values. Suppose g takes a B-value and returns a list of C-values. An ordinary composite g after f is not defined, because f returns a list rather than a single B. We need to map g over all elements of the list, obtaining a list of lists of C-values, then flatten it.

Let's calculate. Let A be the set of ingredients, B the set of dishes, and C the set of shopping items. Suppose f takes rice and returns the list containing stir-fry and soup. Suppose g takes stir-fry and returns the list containing soy sauce and carrots, while g takes soup and returns the list containing broth and herbs. Chaining the operations sends rice to soy sauce, carrots, broth, herbs, in that order.

This operation is often called bind or Kleisli composition. Given f from A to T of B and g from B to T of C for a monad T, bind applies T of g to the structured output of f, creating T of T of C, and then applies the monad's multiplication to flatten it into T of C.

The monad laws guarantee that this composition is associative and that the unit acts as an identity in the appropriate sense. This is the same compositional requirement that defines an ordinary category, now for functions whose outputs carry a structured context.

For the Maybe monad, binding looks simpler. Apply f. If it returns missing, the whole chain returns missing. If it returns present b, apply g to b. This gives us an exact account of failure propagation.

For the list monad, binding distributes over every possible intermediate result and concatenates the resulting lists. It gives us nondeterministic branching with order and multiplicity, not probabilistic choice. If we want probabilities, we need a different mathematical construction with different laws and often additional measure-theoretic assumptions.

## The Kleisli category

For any monad T on a category C, we can build a new category whose objects are the same as those of C, but whose arrows from A to B are arrows from A to T of B in C. These are the structured-output functions we have been composing.

Composition in the new category is the Kleisli operation: first use the earlier structured computation, then lift the next and flatten. The identity arrow at A is the unit map from A to T of A. The monad laws establish the identity and associativity laws needed for a category.

This is a striking return to the first principles of category theory. We began with a desire to make ordinary arrows composable. We then learned how functors change their outputs, how natural transformations compare functors, and how a monad makes a particular family of structured-output arrows compose. The Kleisli category records the resulting composition as ordinary categorical structure.

There is a corresponding construction called the Eilenberg–Moore category, whose objects are algebras for the monad. A T-algebra on an object A is a map from T of A into A satisfying compatibility with the unit and multiplication. For the list monad on Set, these algebras are monoids: a list of A-values is evaluated by multiplying its entries, and the laws enforce identity and associativity.

The Kleisli perspective focuses on computations producing effects. The Eilenberg–Moore perspective focuses on interpreting a structured value inside an algebra. Both arise from the same monad, and they explain different ways the monad participates in categorical constructions.

## Where did the monad come from?

Adjunctions supply a systematic source of monads. Suppose F is left adjoint to U. Then U after F is an endofunctor on the source category of F. The adjunction's unit gives an insertion map from the identity to U F. The counit allows us to collapse U F U F into U F, producing the monad multiplication.

Consider the free-monoid and forgetful adjunction. Starting with a set A, first form the free monoid of words over A, then forget the monoid structure to get a set of lists. That composite is exactly the list functor. The unit inserts a generator as a one-element word. The counit evaluates words of elements of an existing monoid by concatenation or multiplication. Putting these together produces flattening of lists of lists.

The monad laws in this construction follow from the triangle identities of the adjunction. The same triangle identities that said extension and restriction were compatible now guarantee the identities and associativity of flattening. This connection is one reason adjunctions and monads are taught together.

But knowing that every adjunction induces a monad does not mean that every monad has only one adjunction behind it. Different adjunctions can give rise to isomorphic monads. The Kleisli and Eilenberg–Moore constructions provide canonical associated adjunctions under the standard hypotheses.

## A useful failure case

Imagine we define a strange flattening operation for lists that concatenates them but reverses the order of every second inner list. Would that produce a list monad with the usual singleton insertion? We cannot assume so. To be a monad, flattening must be a natural transformation and obey the unit and associativity laws.

Take a list of lists with a single inner list containing a,b. The left unit law says that wrapping that list in an outer singleton and flattening must return a,b. A rule that reverses that inner list would give b,a and fail immediately. Even if a custom rule passed a few tests, the three monad equations must hold for every nested list and every relevant map.

The laws are a specification, not an afterthought. They tell us which implementations can be composed consistently. If a flattening routine violates associativity, the grouping of a larger computation can change its result. If it violates a unit law, inserting a supposedly harmless step can change the answer.

This is an example of mathematics serving software design, though the mathematical model must match the real operational semantics. A pure list monad does not specify execution order on a parallel machine or how external effects interact. Those are extra structures and assumptions that an implementation must supply.

## Why bind is the natural operation to use

The list monad makes it possible to compose functions that return lists. We can derive the Kleisli formula from the two operations we already know, mapping and flattening, rather than memorizing it as a special programming trick.

Let f take A-values to lists of B-values, and g take B-values to lists of C-values. If we apply f to a, we receive a list of B-values. We cannot apply g directly to that list, because g expects a single B. But the functorial action of the list construction tells us how to apply g entry by entry, producing a list of lists of C-values. The multiplication of the list monad then concatenates those lists into one list of C-values.

We should verify associativity on a concrete branching computation. Suppose f sends a particular ingredient to two dishes, stir-fry and soup. Let g send each dish to its required ingredients. Let h send each ingredient to a list of possible shops where it can be bought. If we first combine f and g, we get a flat list of ingredients; applying h and flattening produces all the shop possibilities in an order determined by the branches. Alternatively, combine g and h into one function from dishes to shop lists, then apply that to the dishes returned by f and flatten. Both routes enumerate the same sequence of shops in the same order.

The proof holds because concatenating a list of lists of lists in either order yields the same flat sequence. The monad associativity equation is exactly the general form of that observation. The list monad is sensitive to order: rearranging the order of the original list may change the result. But regrouping the flattening operations does not.

For Maybe, the proof is by cases rather than concatenation. Start with f, then g, then h. If f returns missing, both association orders return missing. If f returns a value but g returns missing, again both return missing. If f and g succeed but h fails, both return missing. If all three succeed, both return the final successful value. Therefore the grouping of bind operations does not affect the result.

This is a good example of how one set of algebraic laws can unify computations that look very different operationally. A list branches. Maybe short-circuits. Both support a consistent notion of composition because their unit and multiplication satisfy the monad laws.

## An algebra for the list monad

There is a useful converse viewpoint. Instead of producing a list, suppose we want to consume a list and reduce it to one value. For a monoid M, we can multiply every entry of a list of M-elements in order, returning the identity for the empty list. Call this evaluation map fold.

To be a list-monad algebra, fold must satisfy two conditions. Folding the singleton list containing m returns m. And flattening a list of lists and then folding it gives the same answer as folding each inner list first and then folding the outer list of those results.

If the monoid operation is string concatenation, the first law says that evaluating the one-element list containing 'cat' returns 'cat.' The second says that concatenating all inner lists into one big list and then concatenating all strings gives the same final string as concatenating each inner list to a string and then concatenating those strings. The two ways of placing parentheses agree because string concatenation is associative.

Now go in the other direction. Suppose a set A is equipped with a map from finite lists of A into A satisfying the two algebra laws. Define a binary operation on A by evaluating a two-element list. Define a candidate identity by evaluating the empty list. The algebra laws imply that evaluating a singleton returns its value and that the binary operation is associative with the chosen identity. Thus a list-monad algebra is exactly a monoid, up to the standard categorical equivalence.

This is more than an analogy between lists and multiplication. It is a reconstruction result: the list monad packages the equations for monoids, and its algebras are ways of interpreting formal words in actual monoids.

## Which computational effects are we modeling?

The examples also show why the word effect should be used carefully. The Maybe monad can model absence or failure information in a pure function, but it does not by itself log errors or execute exceptions. The list monad represents finite branching, but it does not assign probabilities to branches. A state monad can model computations that read and update a state by a function from a state to a pair of result and updated state, but actual concurrent mutation requires additional semantic choices.

For a fixed state set S, a common state construction on Set sends a set A to the set of functions from S into A times S. Such a function takes an initial state and returns a result together with a new state. The unit produces a computation that returns its input value while leaving the state unchanged. Binding executes one state transformer, passes the resulting value to the next, and threads along the updated state.

Take a state consisting of a counter. One computation increments it and returns the old value. Another reads the current counter and returns twice its value. Binding the two ensures the read sees the state after the increment. Associativity says regrouping a chain of such state transformations preserves the result and final state. It does not say the operations commute: switching their execution order may change the answer.

In another setting, a probability-distribution monad replaces finite lists by probability distributions and flattening by averaging a distribution of distributions. This can be made precise for finite probability distributions on sets. More general measurable spaces require attention to measurability and integration. The generic monad pattern survives, but the mathematical category and available operations must be chosen to support it.

## What the laws buy us and what they leave open

Suppose we implement a custom data type that wraps a value with metadata. It is easy to write a map operation, a singleton insertion, and a flattening function. Those names are insufficient to establish a monad. We must verify functoriality, naturality, both unit laws, and associativity. A poorly designed flattening function can lose metadata differently depending on how computations are grouped.

For example, if flattening discards an inner error message when there are two errors, the way nested values are flattened could determine which message survives. That might be a deliberate design decision, but it still must satisfy the appropriate algebraic laws for the intended type of composition. We cannot infer those laws from the fact that the code compiles or returns plausible examples.

The monad structure says that a certain kind of composition is associative and has identities. It does not solve all questions about performance, evaluation strategy, concurrency, error reporting, or user-facing semantics. Those require a specified computational model and often additional algebraic structure.

A particularly useful thing about category theory is that it separates these layers. First we establish the mathematical laws of the intended composition. Then we determine which practical implementations realize the model. The abstraction does not replace engineering judgment; it makes the compositional contract precise enough to test and reason about.

A monad is therefore best learned from the functions it makes composable. Optional lookups, branching lists, and state-transforming computations all supply concrete tests of the laws. The general definition then says exactly which features those examples share, and why they can be organized into categories of structured computations.

## A broader mathematical pattern

A monad can be described as a monoid in the category of endofunctors of C, where the multiplication operation is composition of endofunctors and the unit is the identity endofunctor. This statement becomes meaningful after recognizing that natural transformations serve as the arrows between endofunctors.

What does that comparison buy us? A monoid has an associative multiplication and an identity element. A monad has an associative multiplication that combines two applications of a functor into one, along with a unit that inserts an ordinary object into the functor. The three monad laws mirror the monoid laws exactly, but at the level of functors and natural transformations.

The definition is abstract enough to cover many constructions: free algebraic terms, optional values, lists, state transformations, probability distributions in suitable categories, and more. It does not assert that all these constructions have identical behavior. Each monad packages a different form of structure or computation and a law-abiding method of composing it.

If this feels like a long journey from a missing supervisor record, return to the actual calculation. We wanted to chain two operations that might fail, using one consistent rule rather than rewriting error handling for each pair. The Maybe functor represented possible failure. The unit inserted ordinary successful values. Flattening removed nested optional layers. The laws guaranteed that inserting identities and regrouping chains would not change the result.

That is the mathematical achievement. A monad is a compact recipe for a new notion of composable arrow. Its strength lies in exact algebraic laws that can be checked on small examples and then reused for arbitrarily long chains of structured operations.

## Mathematical companion (display only)

A monad \((T,\eta,\mu)\) on \(\mathcal C\) consists of an endofunctor \(T\), natural transformations \(\eta:1\Rightarrow T\) and \(\mu:T^2\Rightarrow T\), satisfying \(\mu\circ T\eta=1_T\), \(\mu\circ\eta_T=1_T\), and \(\mu\circ T\mu=\mu\circ\mu_T\).

**Maybe:** \(T(A)=A\amalg\{\mathrm{None}\}\), \(\eta_A(a)=\mathrm{Some}(a)\). Flattening \(\mu_A:\mathrm{Maybe}(\mathrm{Maybe}(A))\to\mathrm{Maybe}(A)\) sends \(\mathrm{Some}(\mathrm{Some}(a))\) to \(\mathrm{Some}(a)\) and either missing layer to None.

**Lists:** \(L(A)=\coprod_{n\geq0}A^n\), \(\eta_A(a)=[a]\), \(\mu_A\) concatenates lists of lists.

**Kleisli composition:** For \(f:A\to TB\), \(g:B\to TC\), define \(g\star f=\mu_C\circ T(g)\circ f\). Associativity and unit follow from monad laws.

**From adjunction:** If \(F\dashv U\) with \(\eta:1\Rightarrow UF\), \(\varepsilon:FU\Rightarrow1\), then \(T=UF\) and \(\mu=U\varepsilon F:UFUF\Rightarrow UF\).

### Exercises and answers

1. **Exercise:** What is the Kleisli identity at A? **Answer:** \(\eta_A:A\to TA\).
2. **Exercise:** Does flattening \([[a],[b,c]]\) under the list monad preserve order? **Answer:** Yes, it gives \([a,b,c]\).
3. **Exercise:** In the Maybe monad, what happens to a chain after any missing result? **Answer:** Every subsequent bind returns missing, according to the pure Maybe rules.
